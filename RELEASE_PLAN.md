# План выхода в релиз (SaaS) — CherryPlay v1

## 1. Цель релиза
Состояние продукта, при котором можно уверенно предлагать организаторам вечеринок готовое решение:
- организатор управляет эфиром из **CherryPlayList (desktop)**;
- зрители смотрят страницу вечеринки в **CherryPlayWeb**;
- сервер **CherryPlayServer** обеспечивает хранение плейлиста/метаданных и стриминг состояния воспроизведения.

Фокус v1: **простая продажа "как услуга"**, без биллинга внутри продукта и без сложной модерации.

---

## 2. Границы v1 (MVP)

### 2.1 Must-have (в релиз)
- **Аккаунт организатора** (мульти‑тенантность): один аккаунт = одна организация.
- **Авторизация write-операций**: только организатор может управлять эфиром и обновлять данные (JWT для REST и SignalR).
- **Персистентное хранение** на сервере: метаданные вечеринки + плейлист (без путей к файлам).
- **Две пользовательские веб-страницы**:
  - `party/<shortCode>` — просмотр плейлиста + состояние сессии (если есть).
  - `party/<shortCode>/info` — информация о вечеринке (описание/город/место/дата/расписание/ссылки).
- **Поведение при потере связи**: "заморозка" без блока текущего трека — показываем плейлист и пометки проигранных, а блок "сейчас играет" скрываем.
- **Каталог вечеринок**: общая витрина всех организаторов, но **по умолчанию вечеринка unlisted** (только по ссылке). Включение в каталог — решает организатор.
- **Синхронизация плейлиста**:
  - в режиме редактирования: публикация на сервер **по кнопке Publish**;
  - в режиме сессии: изменения плейлиста и состояния идут **live**.
- **Хранение "навсегда"** до удаления организатором (в v1 без автоархивации).
- **Anti-abuse минимум**: простое rate limiting на публичные ручки/хаб + лимиты по вечеринкам (чтобы каталог нельзя было "заспамить").
- **Операционка**: health-check, минимальные логи, регулярный бэкап БД (еженедельно).

### 2.2 Not now (явно откладываем)
- Биллинг/подписки в продукте.
- Приватный режим для зрителей (PIN/логин зрителя).
- Команды/несколько сотрудников на один аккаунт.
- Полноценная админка платформы (всё, что можно делать вручную — делаем вручную).
- Брендинг/приватные темы как продаваемая фича — **MVP реализован** (см. [FEATURE_THEME_MONETIZATION.md](./FEATURE_THEME_MONETIZATION.md)); дальнейшее развитие (биллинг и self-service) остаётся вне v1.
- Custom domains (закладываем совместимую маршрутизацию и модель, реализацию — позже).
- Email-верификация при регистрации (по-прежнему вне v1).

## 3. Ключевые продуктовые решения (фиксируем до реализации)

### 3.1 Идентичность вечеринки и ссылки (дорого менять после релиза)
- Внешняя ссылка для зрителя: **`party/<shortCode>`** (+ `/info`).
- `shortCode`:
  - уникальный, короткий, устойчивый к "похожим символам" (0/O, 1/l и т.д.);
  - неизменяемый после создания;
  - используется в каталоге и шаринге.

### 3.2 Данные, которые храним на сервере (минимум)
- Вечеринка: название, описание, организатор/место/город, дата/расписание, тема, флаг "в каталоге", shortCode.
- Плейлист: только отображаемые поля (id, name/title, duration, структура групп), без абсолютных путей.
- Состояние сессии: минимум для отображения зрителю (played/disabled, статус "сессия активна/нет", последнее известное состояние).

### 3.3 Связь локального проекта и серверной вечеринки
- Поток: "создать на сервере → сохранить `partyId` в локальном проекте".
- Локальный проект — **истина**: publish в edit перетирает серверную версию.

## 4. Архитектура v1 (по подсистемам)

### 4.1 Accounts & Auth (Server)
- Вход организатора: **email+пароль** (логин/регистрация) и OAuth 2.0 провайдеры **VK**, **Mail.ru**. **OAuth2 для Telegram откладывается** на последующие версии.
- JWT:
  - access token для API и SignalR;
  - хранение в вебе через **httpOnly cookie**;
  - политика обновления токена: простая (без refresh-токенов); после сброса/смены пароля все сессии инвалидируются → повторный вход.
- Сброс/смена пароля (**shipped** end-to-end): Server (эндпоинты + RuSender) + CherryPlayComponents + Web (`/forgot-password`, `/reset-password`, смена в кабинете) + List (запрос forgot + change-password в Account). Ссылка из письма всегда на Web; после reset/change — инвалидация всех сессий. Email-верификация при регистрации — по-прежнему вне v1 (§2.2).
- Роли:
  - organizer (владелец данных и write‑доступ);
  - viewer (анонимный, read‑only через public API и Hub).

### 4.1.1 Логин в CherryPlayList (desktop, organizer)
- UI: экран "Аккаунт" (войти/выйти; выбор: email+пароль или OAuth — VK/Mail.ru; текущий организатор). OAuth через Telegram в v1 отложен.
- Поток входа по OAuth (VK, Mail.ru):
  - пользователь выбирает провайдера (VK или Mail.ru);
  - приложение открывает системный браузер на `auth/{provider}/start` (например `auth/vk/start`);
  - после успешного входа провайдер делает redirect обратно в приложение:
    - через custom URL scheme (например `cherryplaylist://auth?...`), либо
    - через локальный callback `http://127.0.0.1:<port>/callback` (на время логина);
  - приложение извлекает `code` и `provider` из redirect и вызывает `POST /auth/exchange` с телом `{ code, provider }`.
- Использование токена:
  - REST запросы организатора: Bearer JWT;
  - SignalR write‑операции: JWT передаётся при подключении к Hub и валидируется сервером.
- Хранение токенов: предпочтительно защищённое хранилище ОС (Windows Credentials и аналоги).
- Истечение токена: допускается "простая" стратегия v1 (достаточный TTL на мероприятие или ручной ре‑логин). **Refresh‑токены** — позже. Self-service forgot/change-password — shipped (см. §4.1); после сброса/смены — повторный вход.

### 4.1.2 Логин в CherryPlayWeb (organizer)
- Веб‑кабинет организатора использует httpOnly cookie (без доступа JS к токенам).
- Вход: по email+паролю или выбор провайдера (VK, Mail.ru) и переход на `/auth/{provider}/web` (например `/auth/mailru/web`).
- После авторизации провайдер делает redirect на `/auth/{provider}/callback`, сервер устанавливает httpOnly cookie.
- Кабинет организатора: метаданные/публикация, без управления эфиром; смена пароля — в кабинете.
- Восстановление пароля (live): `/forgot-password`, `/reset-password?token=` (письмо → Web); детали — [accounts-and-auth.md](docs/integration/accounts-and-auth.md).

### 4.2 Party Management (Server + Web)
- Кабинет организатора (минимум):
  - профиль (название/лого/ссылки);
  - список своих вечеринок;
  - управление публичностью (unlisted/catalog);
  - создание/редактирование метаданных вечеринки;
  - удаление вечеринки.
- В кабинете организатора v1 **нет управления эфиром** (сессией) — только метаданные/публикация.
- Лимиты v1:
  - ограничение "будущих" вечеринок (например, 2) на организатора;
  - повышение лимита — вручную (без админки).

### 4.3 Streaming (Desktop ↔ Server ↔ Web)
- Write только от организатора (JWT).
- Viewer подключается по shortCode, получает:
  - плейлист (через API) и/или последнее сохранённое состояние;
  - живые обновления по SignalR при активной сессии.
- Позиционная точность: "в целом совпадает" (без жёсткого требования к секундам).
- Offline/freeze:
  - при потере организатора/сервера: UI скрывает блок текущего трека;
  - плейлист остаётся видимым, played‑пометки остаются.

### 4.4 Branding (Organizer + Party)
- Модель брендинга двухуровневая:
  - дефолт на уровне organizer;
  - override на уровне party (опционально).
- В v1 брендинг в вебе: логотип + имя организатора (и базовые поля info).
- Темы/кастомизация: хранить настройки можно; monetization MVP (пакеты тем, entitlement, private/public visibility) реализован и описан в [FEATURE_THEME_MONETIZATION.md](./FEATURE_THEME_MONETIZATION.md).

### 4.5 Ops (SaaS)
- Один сервер/инстанс (монолит).
- Health endpoint и базовые логи событий (auth, create/update party, start/end session, подключение к Hub).
- Бэкап БД: минимум еженедельный + инструкция восстановления.

## 5. Принятые допущения v1 (чтобы план был проверяемым)
- Масштаб: до ~50 одновременных зрителей на вечеринку.
- Точность позиции: "в целом совпадает" (без строгих требований к секундам).
- Надёжность: сервис **не должен падать во время вечеринки**; при проблемах сети — корректный freeze UI у зрителя.

## 6. Контракты v1 (кратко, без деталей реализации)

### 6.1 Public (viewer)
- Получить вечеринку по `shortCode` (метаданные + флаг "в каталоге").
- Получить плейлист по `shortCode`.
- Получить список вечеринок каталога (только включённые организатором).
- Подключиться к SignalR как viewer по `shortCode` и получать обновления состояния (если активна сессия).

### 6.2 Organizer (authorized)
- Логин/логаут (email+пароль и OAuth: VK, Mail.ru; Telegram OAuth2 отложен).
- Сброс пароля (forgot/reset, без auth) и смена пароля (authorized); детали и статусы — [CONTRACTS.md](CONTRACTS.md) §3.2.0a; клиенты — [accounts-and-auth.md](docs/integration/accounts-and-auth.md).
- Управление профилем организатора (имя, логотип, ссылки).
- CRUD вечеринок (создать/редактировать метаданные/удалить).
- Toggle: unlisted ↔ в каталоге.
- Publish плейлиста (edit mode).
- Live write событий сессии/состояния (session mode) — только с авторизацией.

## 7. План работ (эпики)

### Epic A — Персистентность и миграции (Server)
- Подключить реальную БД + миграции.
- Репозитории для organizer/party/playlist/session state.
- Политика удаления данных организатором.

### Epic B — Accounts & Auth (Server + Web)
- Вход по email+паролю (логин/регистрация). OAuth 2.0 провайдеры: VK, Mail.ru (OAuth2 для Telegram откладывается).
- JWT для REST + SignalR.
- Web: сессия через httpOnly cookie.
- Минимальные экраны: login (с выбором провайдера), logout, "мой кабинет".
- Self-service сброс/смена пароля (Server + RuSender + Components + Web + List) — **доставлено**; email-верификация при регистрации — вне v1.

### Epic C — Party management (Web + Server)
- Organizer profile (лого, имя, ссылки).
- CRUD вечеринок (создать/редактировать метаданные/удалить).
- Toggle "в каталоге" vs "unlisted".
- Лимит будущих вечеринок.

### Epic D — Каталог и публичные страницы (Web + Server)
- Общий каталог публичных вечеринок (все организаторы, только те, что включены в каталог).
- Страницы `party/<shortCode>` и `party/<shortCode>/info`.
- SEO/шаринг можно минимально (без heavy‑маркетинга).

### Epic E — Desktop интеграция (CherryPlayList)
- Привязка partyId к локальному проекту.
- Edit: Publish кнопкой.
- Session: live sync состояния и плейлиста.
- Поведение при ошибках/разрывах (best effort, но без "падений во время вечеринки").

### Epic F — Streaming устойчивость (Server + Web)
- Реконнект веб-клиента.
- Запрос полного состояния после реконнекта.
- Freeze-поведение (скрыть текущий трек при оффлайне).

### Epic G — Релизная готовность (Ops + QA)
- Чеклист деплоя и отката.
- Smoke‑тесты "перед мероприятием".
- Минимальные алерты (хотя бы health + ручной мониторинг логов).

## 8. Критерии "готово к продажам"

### 8.1 Безопасность
- Зрители не могут отправлять write-события.
- Организаторские write-действия требуют валидной авторизации.
- Данные организаторов изолированы (организатор видит/правит только своё).

### 8.2 Надёжность "на вечеринке"
- При обрыве связи зрителю показывается корректное freeze‑состояние (без "битого UI").
- Сервис не теряет плейлист/метаданные при рестарте сервера.
- Минимальный путь восстановления: поднять сервис + восстановить БД из бэкапа.

### 8.3 UX
- Публичная ссылка стабильна (`party/<shortCode>`).
- Понятно, где "инфо" и где "плейлист".
- Организатор может сам: создать вечеринку, заполнить инфо, включить в каталог, удалить.

## 9. Риски и "дорогие изменения" (держать под контролем)
- Формат shortCode и маршруты страниц (публичные ссылки).
- Контракты сообщений SignalR и публичных DTO.
- Модель данных (organizer/party/playlist/session) и миграции.
- Модель авторизации (JWT, cookies, разграничение write/read).
- Каталог: политика публичности по умолчанию и антиспам/лимиты.
